Modify the GET handler to support real pagination:

1. **Parse page and limit from searchParams** — Add query param parsing:
   ```typescript
   const page = Math.max(1, parseInt(searchParams.get('page') || '1', 10));
   const limit = Math.min(200, Math.max(10, parseInt(searchParams.get('limit') || '50', 10)));
   ```
   Default: page=1, limit=50. Max limit=200 to prevent abuse.

2. **Add COUNT query** — Before the main SELECT, run a COUNT(*) query with the same WHERE clause:
   ```sql
   SELECT COUNT(*)::int as total FROM product_registry pr WHERE ${whereClause}
   ```
   Use the same `params` array.

3. **Add LIMIT/OFFSET to main SELECT** — Append to the existing query:
   ```sql
   LIMIT $${paramIdx} OFFSET $${paramIdx + 1}
   ```
   Add `limit` and `(page - 1) * limit` to params array.

4. **Update pagination response** — Replace the hardcoded pagination:
   ```typescript
   pagination: {
     page,
     limit,
     total,
     pages: Math.ceil(total / limit),
   }
   ```

5. **Keep summary query unchanged** — The summary (total_products, with_anvisa, total_quantity) should still use the full WHERE clause without LIMIT, as it shows aggregate stats for the filtered set.

6. **Backward compatibility** — If no `page` param is provided, default to page=1 with limit=50 (current behavior returns all, but this is the optimization we want). If frontend needs all products for export, it should use a separate `?export=true` param or a dedicated export endpoint. For now, just implement pagination.
